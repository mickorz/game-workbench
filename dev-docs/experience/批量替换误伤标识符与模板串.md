# 批量替换品牌词误伤标识符与模板字符串

## 问题现象

P1 品牌批量替换（`OhMyGame` → `XC-UI-Flow`）后 `bun run typecheck` 报大量语法错：
`TS1005: ',' expected`、`TS1128`、`TS1434`，集中在 `src/daemon/agent.ts`、`pi-agent.ts` 等；
后续 vitest 又冒出 `expected 'XC-UI-FlowDefault' to be 'XcFlowDefault'` 断言错。

## 排查过程

1. `git stash` 基线验证：干净树 typecheck 通过 → 是替换引入。
2. 看报错行：`ensureXC-UI-FlowPiEnvironment`、`withoutXC-UI-FlowManagedPiPackages` —— 驼峰符号里的 `OhMyGame` 被换成带连字符的品牌词，非法标识符。
3. 修标识符用正则 `(?<=[A-Za-z0-9_$])XC-UI-Flow|XC-UI-Flow(?=[A-Za-z0-9_$])` → `XcFlow`，但该正则又误伤两类：
   - 测试断言里的**字符串** `"XC-UI-FlowDefault"`（品牌词后跟字母即命中）；
   - 模板串 `` `could not ${action} OhMyGame${detail} `` —— `$` 是标识符字符，`${` 前的品牌词被当标识符替换。

## 根因

品牌词替换是**语义敏感**操作：`OhMyGame` 既出现在用户文案里，也出现在驼峰标识符、模板字符串、i18n key 里；纯文本替换与「标识符上下文正则」都会各自误伤另一类。

## 解决方案

- 标识符级：`XcFlow`（合法驼峰，与 installer 的 `XcFlowInstallProgress*` 一致）。
- 文案级：`XC-UI-Flow`。
- 分两轮收敛：先全局换文案词，再用标识符上下文正则修符号；**修完必须 grep 复扫** `XcFlow${`、`}XcFlow`、`"XcFlow[A-Za-z]"` 三类误伤。
- 测试期望值与源码字符串按语义人工对齐（`onboarding-renderer` 的 `"XC-UI-FlowDefault"`、`external-agent-clients` 的错误消息模板）。
- 向导模板（AGENT_INSTRUCTIONS/PROJECT_DOCUMENTATION）内容变化后，测试指引是**旧 hash 进 `PROJECT_GUIDE_UPGRADES`、新 hash 记录进测试**（保证存量工程可升级），不是改断言了事。

## 预防/注意事项

- 大批量品牌/符号替换一律 python 脚本 + write 工具（含反引号/正则的改写禁 bash inline）。
- 替换前先 grep 出**全部出现形态**（纯文案 / 驼峰符号 / 模板串 / i18n key / 协议 id），分类定替换词表再动手。
- typecheck/test 单独跑并看 **exit code**，禁止 `cmd | tail && echo`（管道吃掉非零退出码，P0 就踩过一次）。
- 本仓库测试真 runner 是 `bun run test`（vitest）；`bun test` 是 bun 自带 runner，会扫进 `thirdparties/` 子模块测试、缺 `vi.waitFor`，**不要用 `bun test` 做验收**。

## 补遗（2026-11-03，插件清单目录改名）

- 双落读取改写时的隐形语义：「文件不存在」在原逻辑里可能是**正常分支**（如 portability 的 backup——非本应用导出的插件包本就无 backup）。把「无文件」从 ENOENT 容错改成显式报错，会打断原本合法的导入。改双落前先确认原 catch 的每个分支语义。
- 复制后写新名 = 双清单并存：copyForAuthoring 先 cp 整目录（旧名清单随行）再写新名清单，必须先删旧名清单文件，否则归档里两份清单。
