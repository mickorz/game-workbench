# FGUI 美术流程 · s2「FGUI 落位」

> **路径约定（先读）**
> - **工作区根** = 含 `.opencode` 的那层（本工程 = `自动化流程/`）。**它是所有相对路径与命令的基准**，每条命令都在这里执行（bash 工具的 `workdir` 设为工作区根，不要靠 cd）。
> - **真实 FGUI 工程根 = `client_dir`**（`assets/` + `settings/` + `*.fairy` 所在层），由 s0 写进 `.opencode/workspace.json`。先跑 `python .opencode/lib/workspace.py where` 看它；要改的是 **client 工程**，不是工作区根。
> - **需求产物 = `.opencode/work/<game_key>/<需求>/`**（清单/施工单/占位/快照/PSD 都在里面）；实际路径用 `python .opencode/lib/workspace.py where --需求 <需求>` 核对。
> - 技能脚本住**本技能目录** `.opencode/skills/fgui-flow/scripts/`；共享库在 `.opencode/lib/`。
> - 脚本**不写死任何工程名/路径**：靠 `workspace.py`（读 `client_dir`，缺则退回"向上找 `*.fairy` + `assets/`"）定位工程，也可显式 `--root <工程根>`。
> - 定位不到工作区根时，命令要在**含 `.opencode` 的那层**跑，或给 `scan/lookup/knowledge` 加 `--root`。

## 先记住四件事

1. **s2 只是全流程的一环**：`s0-env 环境配置 → s1-req 解析需求 → s2-fgui 改工程 → s3-to-psd 出 PSD 还原稿 → s4-psd 改样式切图`。**s2 不再自己抄需求/出指导文档** —— 需求解析上移到 s1；s2 **消费 s1 的产物**。
2. **规矩最高优先级**：`fgui文档/00-核心流程总纲.md`；**详细手册** `fgui文档/01-操作手册.md`（这两份是人类文档，跟运行时无关）。工作区根 `AGENTS.md` 每次会话自动加载，那 9 条硬规矩任何时候都成立。
3. **知识库要现读**（`.opencode/knowledge/*.md` 会持续更新；用到时现读，**不凭记忆、不把内容抄进技能**）：涉及"这个效果该用哪种手法 / 要不要出新图 / **位置怎么排**"之前，先
   ```powershell
   python .opencode/skills/fgui-flow/scripts/knowledge.py --list           # 索引（文件 + 标题树）★主题词从这来
   python .opencode/skills/fgui-flow/scripts/knowledge.py --topic 复用 --topic 九宫格   # 例子，不是全集
   python .opencode/skills/fgui-flow/scripts/knowledge.py --topic 对齐 --topic 留白     # 例子，不是全集
   ```
   ⚠ **例子不是全集** —— 知识库随时会多出新文件/新小节；主题词**以当次 `--list` 索引里的标题词为准**。**落位改坐标前，务必再查一次排版类主题（对齐 / 成组 / 留白 / 间距 / 居中 / 锚点）。**
   知识库**唯一一份** = `.opencode/knowledge/`（`knowledge.py` 只读这里；找不到会退回本包自带快照，不会报错）。
4. **只用实测事实**：节点名/坐标/资源 id/图片尺寸一律用 `lookup.py` 或读 XML，**不凭记忆**。

## s2 内部阶段（无名，按顺序）

| 阶段 | 干什么 | 命令/脚本 | 产物 | 出口条件 |
|---|---|---|---|---|
| **备事实底座** | 工程改过才重扫 | `scan_fgui.py` | `.opencode/work/facts.json` + `工程结构.md` + `美术资源清单.md` | `lookup.py --check` 说新鲜 |
| **出方案** | 读 s1 的清单/施工单 → 核实 → 连贯写方案 | `lookup.py` + 手写 | `<需求>/方案.md` + `<需求>/备份/` | 方案完备直接进入占位与落位 |
| **定种类·占位·清单** | 缺图 → 资源种类表 + 占位 + 回填清单 | `placeholder_png.py` + `workspace.py manifest-*` | **资源种类表** + `<需求>/清单.json|md` + `<需求>/占位/`（并覆盖 client 工程 `assets/<包>/atlas/`） | 种类与规格＝真东西的规格；替换不改节点 |
| **落位执行** | 改 client 工程（先备份） | 改组件 XML + `package.xml` | 改好的**工程文件**（**先不写文档**） | 🔒 **单一闸门：人看一眼效果** |
| **补文档** | 定稿后一次性补齐（含 PSD 衔接文档） | `generate_psd_spec.py` | 校验报告 + **修改清单** + 交付说明 + **psd-spec.json** | 客观事实齐备，定稿快照生成 |
| **交程序** | 交工程 + 建快照 | `workspace.py snapshot` | `<需求>/FGUI/` 快照 + FGUI 工程文件 + 交付说明 | 程序能打开、说得清哪块归他 |

> 记法：**扫 → 出方案 → 占位 → 落位 → 补文档 → 交付**。
> **文档时机（重要）**：方案确认后**直接把工程文件改出来**给人看；**效果定稿前不要写清单 / 交付说明**（写一次就得跟着改一次，纯浪费）。人点头后再一次性补齐。
> 真图什么时候出由**人**定；占位图先让工程跑通，真图出来**同名替换**，工程结构不再动。

> **产物落点**：本次需求的一切派生物（`清单.json`/`清单.md`、工程快照、PSD、切图、占位）都落在 **`.opencode/work/<game_key>/<需求>/`**（路径见 `python .opencode/lib/workspace.py where --需求 <需求>`）。`.opencode/`、`fgui文档/` 都是工作层，**不进交付**。

## 每个阶段怎么做（命令可直接跑）

### 备事实底座
```powershell
python .opencode/skills/fgui-flow/scripts/scan_fgui.py        # 在工作区根执行；自动定位 client_dir，输出到 .opencode/work/
python .opencode/skills/fgui-flow/scripts/lookup.py --check   # 看底座还新鲜吗（退出码 1 = 缺失/过期，重扫）
```
只在工程被改过之后重扫；平时定位读 `facts.json`，不重扫。事实底座（`facts.json`/`工程结构.md`/`美术资源清单.md`）**project 级**，落在 `.opencode/work/` 顶层。

### 出方案（消费 s1 的产物）
```powershell
python .opencode/lib/workspace.py where --需求 <需求>          # 需求目录 = .opencode/work/<game_key>/<需求>/
python .opencode/skills/fgui-flow/scripts/knowledge.py --topic 复用 --topic 九宫格   # 现读知识库
python .opencode/skills/fgui-flow/scripts/lookup.py <关键词>                    # 定位（退出码 3 = 没命中）
python .opencode/skills/fgui-flow/scripts/lookup.py --comp <组件名> --nodes      # 某组件全部节点
```
1. **先读 s1 的产物**：`.opencode/work/<game_key>/<需求>/清单.json`（机器真源，决定"要产出哪些资源"）+ `施工单.md`（人读版，含需求逐条 / 已确认结论 / 决定清单）。**没有就先跑 `/s1-req`**，不要自己手抄需求截图。
2. 用 `lookup.py` 把每条需求核实到**具体文件 + 节点**。
3. 写 `<需求>/方案.md`，**十三节缺一不可**：改动总账 / 坐标系与算式 / 逐节点改动表（现值→新值→为什么）/ 布局图 / 其它联动文件 / 新图与登记 / 施工步骤+闸门 / 校验清单（结构·尺寸·落位·需求对照·范围·引用）/ 回退方案 / 交付说明 / 风险 / 待确认 / 不做的事。
4. **同时**把要改的 XML 备份到 `<需求>/备份/`。
5. **不设方案等待闸门**：写完方案后自动直接进入"定种类·占位·清单"与"落位执行"阶段，改出工程后再给人看。

**纪律**：美术需求为准 → 冲突记进方案；**需求写明的不问**；"需求没说且影响施工"的进"待确认"并**一次问清**；**运行时逻辑不写进待确认**（只写交付说明"归程序"）。

### 定种类·占位·清单
先过**复用决策顺序**（下面），走到底才生图。

**① 资源种类表（硬动作，跳过它就要返工）**：动工之前，把本次要产出的**每一个**资源列成一张表，四条都要写死：

| 列 | 写什么 | 例子 |
|---|---|---|
| **种类** | 图片 / 九宫格图 / 非等比拉伸 / **位图字体＋字形** / 组件 / 复用现成 | 「漂」＝**位图字体**（不是图片，也不是普通文字） |
| **最终文件名＝槽位名** | 替换时用的名字（含目录） | `fnt/piao.fnt` ＋ `fnt/piao/p.png` |
| **规格** | 尺寸、九宫格边距、字形高度、字符表 | 字形高 69（与 `win.fnt` 对齐）、字符 `0-9`＋`p` |
| **谁产出** | 人（美术/字体）／AI 生图／我从现成里复用 | 位图字体＝人出；标签图＝AI 生图 |

> **为什么**：种类定错＝返工。种类＋规格先定死，① 后面替换**同名同规格、不用改节点**；② 这张表**就是生图/出字体的方向单**。

**② 同时写清单（三技能交接棒）**：种类表定完，把每个要产出的资源**同步**写进 `<需求>/清单.json`，并生成 `清单.md`：

```powershell
# <需求> 目录 = .opencode/work/<game_key>/<需求>/
python .opencode/lib/workspace.py where --需求 <需求>     # 先确认实际路径
python .opencode/lib/workspace.py manifest-init <需求>
python .opencode/lib/workspace.py manifest-add <需求> --槽位名 assets/<包>/atlas/img_x.png --种类 图片 --尺寸 96x33 --透明底 true --用途 "XX节点" --来源 AI生图
# 九宫格：--种类 九宫格图 --九宫格 20,20,20,20 ；位图字体：--种类 位图字体 --字形高 69 --字符表 0-9,p
python .opencode/lib/workspace.py manifest-md <需求>       # 由 json 生成 清单.md
```
> 清单字段/枚举（种类·来源·状态）见 `python .opencode/lib/workspace.py manifest-add --help`。s3/s4 会**回填** `psd`/`切图`/`来源`/`状态`。

**③ 占位落两处**：占位图既落 `<需求>/占位/<槽位名>`（留存档），又**同名覆盖 client 工程 `assets/<包>/atlas/`**（工程要能跑）。文件名＝槽位名，规格＝最终规格。

```powershell
# 占位：先落 <需求>/占位/<槽位名>，再同名覆盖到 client 工程 assets/<包>/atlas/
python .opencode/skills/fgui-flow/scripts/placeholder_png.py --size 96,33 --out "<需求>/占位/atlas/img_x.png" --label "TAG_X 96x33" --purpose "待 AI 真图同名替换"
Copy-Item "<需求>/占位/atlas/img_x.png" "<client_dir>/assets/<包>/atlas/img_x.png"
# 九宫格占位（把拉伸区画出来）：
python .opencode/skills/fgui-flow/scripts/placeholder_png.py --size 300,120 --out "<需求>/占位/atlas/img_panel.png" --scale9 20,20,20,20 --label NEW_PANEL
# 位图字体占位：字形放 <包>/fnt/<字体名>/<字符>.png，再写 <包>/fnt/<字体名>.fnt（照 win.fnt 的格式）
```
> `<client_dir>` 用 `python .opencode/lib/workspace.py where` 打印的实际路径替换。

**④ 顺带查素材库（可选）**：报"要 AI 生图"之前，先看一眼 PSD 素材库有没有可复用稿，命中就预填候选（**最终以 s4 的取件查询为准**）：
```powershell
python .opencode/lib/workspace.py find-asset <需求>
```
要生图就必须**规格给全**：尺寸 / 透明底 / 是否九宫格 / 数量 / 命名（＝最终文件名）/ 风格参照。带文字的小图要提醒"AI 写中文易错字、改文案要重画"，能给"底图+文字节点叠字"的方案就给；**成词/成套的字形（如「封顶」「漂」）优先考虑位图字体或复用现成字形**。

### 落位执行
按方案逐节点改 **client 工程** 的 `assets/<包>/component/*.xml` 与 `<包>/package.xml`，**直接把工程文件改出来**（改前先备份到 `<需求>/备份/`）。
**这一轮先不写"校验报告 / 修改清单 / 交付说明"** —— 只保证工程文件是对的。
**改完停下来给人看一眼效果 → 单一闸门。**

### 补文档（人确认 OK 之后才做，只做一次）
效果确认"没问题、这版定稿"了，再一次性补齐（都在 `<需求>/` 下）：
- **校验报告**（`<需求>/校验报告.md`）：六类 —— 结构 / 尺寸 / 落位 / 需求逐条对照（已落·未落＋原因）/ 范围（只有方案里列的文件被动过）/ 引用（新 id 不冲突、老资源没被破坏）；
- **修改清单**（`<需求>/修改清单.md`）：一条需求一行 —— 状态 + 现值 + 在哪个节点 + 归谁，人拿它对着编辑器核；
- **PSD 衔接文档**（`<需求>/psd-spec.json`）：
  ```powershell
  python .opencode/skills/fgui-flow/scripts/generate_psd_spec.py <需求> [--view <组件XML>]
  ```
  导出客观事实结构（节点、坐标、尺寸、类型、是否复用、是否九宫格），**严禁提前包含【新】标签**，专供 s3 消费；
- **交付说明**：见下一阶段。

> 迭代期间**不要反复更新这些文档**：它们是"定稿快照"，只在人点头后产出一次；之后每轮只更新这一份。
> 若编辑器又保存过，现值以清单为准，并注明上次校验的哪些断言已失效。

### 交程序
交付物＝**FGUI 工程文件**（`assets/` + `settings/` + `*.fairy`）+ 交付说明（新节点名 / 新图文件名+id / 控制器页值约定 / 哪些显示条件归程序 / 哪些是"需求没说所以先这样"）。`.opencode/`、`fgui文档/` **不进交付**。

**交付前建工程快照**（只本轮涉及的包；供 s3/s4 读）：

```powershell
python .opencode/lib/workspace.py snapshot <需求>     # 不给 --packages 就从 清单.json 推断本轮包
```

> 快照落到 `<需求>/FGUI/`（`assets/<本轮包>` + `settings/` + `*.fairy`）。s3 从快照读界面 XML；**交付本体仍是 client 工程根**。

> **可选下游（提示一下，不自动做）**：交付完 FGUI 工程后，如果还需要给美术出一份**可直接改图的 PSD 还原稿**，提示用户运行 `/s3-to-psd <需求> <界面 XML 路径>`（加载 `fgui-to-psd` 技能）。**还原哪个界面由用户点**，不自动全出。产物落 `<需求>/psd/还原稿/`。

## 单一闸门（落位后必须停下来给人看）

- **出方案后不设闸门**，直接连贯执行落位；
- **落位完成（落位执行末）** → **唯一闸门**：人看一眼效果（占位图阶段就能在编辑器看布局）。
- **闸门通过之前只出效果**（工程文件），**不写清单 / 交付说明 / psd-spec.json**；人点头后再一次性补齐（补文档）。
- 其余步骤不要反复确认；**需求已写明的事不问**。

## 复用优先：要新图之前的 7 级决策（成本从低到高）

1. 改现有节点的尺寸/位置/颜色/透明度 →
2. 九宫格拉伸（先看 `package.xml` 有没有 `scale9grid`）→
3. 非等比拉伸 `fill="scaleFree"` / 缩放 / 镜像 / 旋转 / 变色 `gearColor` →
4. 换一张已有的相似图 →
5. **复用现成的通用件（组件）** →
6. 用文字节点顶掉图 →
7. **以上都不行才 AI 生图**。

### 第 5 级：先看通用件，**能不能复用由需求的结构决定**

**判断口径：拿需求要的"结构"去对通用件的"结构"** —— 不是看"是不是按钮"这个词。

- **对得上 → 复用**：需求要的只是通用件已有的东西（底图 + 居中文字，换个字/换张图/改个色都算）。典型：确认 / 取消 / 关闭 / 继续 这类普通方按钮 → 直接在**实例**上覆盖 `icon` / `title` / `titleColor` / `titleFontSize`，**不改通用件本身**。
- **对不上 → 照需求单独建组件**，别把需求硬塞进通用件。典型：**多状态卡牌**（按状态换图 / 换字色 / 显隐角标）。硬套通用件＝**把状态结构丢掉**。
- **拿不准就把两边结构摆出来问一句**，别默认复用。

- **复用白拿的东西**：底图随 `size` 自动铺满、文字自动居中、按下反馈、控制器页值。
- **跨包引用要写 `pkg="<8位包 id>"`，且目标组件要勾「导出」** —— 漏任一项会**静默失效**（不报错、什么都不显示，很难查）。
- **完整清单（id / 引用写法 / 坑 / 其它通用件：弹层底·头像·手牌·流水条…）现读知识库，不要凭记忆**：
  ```powershell
  python .opencode/skills/fgui-flow/scripts/knowledge.py --topic 通用件 --topic 复用
  ```
- 这一级**不只是按钮**：需求里出现的控件，**先查一遍知识库的通用件清单再决定要不要新建**。

报新图时必须说清"试过哪几种手段、为什么不行"。改共用图/通用件前先查引用（`lookup.py Button9Scale`），共用资源一改会影响**所有**引用它的界面。

## 常见情况怎么办（详见 `fgui文档/01-操作手册.md` §六）

| 情况 | 处理 |
|---|---|
| 需求只有截图没文字 | 逐条抄成 md 再解析（在 s1 做），抄时标出疑似错别字/漏项 |
| 美术需求与策划案冲突 | 美术需求为准，冲突记进方案 |
| 怀疑错别字（如"捉跑胡"） | s1 已跑 `check_terms.py`；这里按正字做并记录（原文照抄不改） |
| 需求没说但影响施工 | 进"待确认"，一次问清；**逻辑类不问**，写交付说明 |

| 真图没出、看不出对错 | 用占位图先跑通布局（这正是占位图的用途） |
| "数量变了"（4 人改 3 人、列表加行） | 间距先找包裹组的 `layout`+`lineGap`；隐藏靠 `gearDisplay` + `excludeInvisibles="true"`（剩下的**自动靠上**）；分隔线/箭头等绝对定位装饰要单独挪；外层 View 用 `relation` 自适应 |
