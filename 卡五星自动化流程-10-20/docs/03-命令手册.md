# 03 · 命令手册

## 1. 命令是怎么跑起来的

opencode 会加载项目里的：

```
.opencode/command/s0-env.md
.opencode/command/s1-req.md
.opencode/command/s2-fgui.md
.opencode/command/s3-to-psd.md
.opencode/command/s4-psd.md
```

对应斜杠命令：

```
/s0-env     /s1-req     /s2-fgui     /s3-to-psd     /s4-psd
```

命令文件只做两件事：

1. 用 `skill` 工具加载对应技能；
2. 把 `$ARGUMENTS`（你在命令后面写的内容）交给技能。

**命令 ≠ 立刻改工程**。真正的步骤、纪律、脚本调用都在技能 `SKILL.md` 里；s2 只有落位完成后的那一道人工闸门。

## 2. 总表

| 命令 | 对应技能 | 典型输入 | 主要产物 | 下一步 |
|---|---|---|---|---|
| `/s0-env` | `fgui-env` | 可选 `--client <路径>` | `workspace.json` 的 `client_dir` | `/s1-req` |
| `/s1-req` | `fgui-req` | Excel 在 `inbox/`，或手工需求目录 | `需求.md`、`参考图*/`、`清单.json`、`施工单.md` | `/s2-fgui` |
| `/s2-fgui` | `fgui-flow` | 需求名 / 施工单 / 截图 | 改好的 client 工程、`方案.md`、`占位/`、`FGUI/`、`psd-spec.json` | `/s3-to-psd` |
| `/s3-to-psd` | `fgui-to-psd` | 需求名 / `psd-spec.json` / 界面 XML | `psd/还原稿/*.psd` | `/s4-psd` |
| `/s4-psd` | `psd-style` | 需求名 / 源 PSD / 要改什么 | `psd/制作/`、`切图/`、回写工程 | 交付 |

自然语言触发也可以，agent 会按 `AGENTS.md` 的触发词表对号：

| 你说 | 走哪步 |
|---|---|
| 环境配置 / 定位工程 / 第一次配置 | s0 |
| 解析需求 / 拉需求 / 导入需求 | s1 |
| 新需求按流程做 / 按 s2 落位 / 继续推进这个需求 | s2 |
| 出 PSD 还原稿 / 还原成 PSD / FGUI 转 PSD | s3 |
| 改样式 / 切图 / 导出透明图 | s4 |

## 3. `/s0-env` 环境配置

**目的**：定位真实 client 工程，写 `workspace.json`。只改 `.opencode/`，不碰 client 工程。

**用法**：

```text
/s0-env
/s0-env --client "D:\path\to\client\42324"
```

**脚本等价**：

```powershell
python .opencode/lib/workspace.py env --check
python .opencode/lib/workspace.py env
python .opencode/lib/workspace.py env --client "D:\path\to\client\42324"
python .opencode/lib/workspace.py where
```

**成功标准**：

- `where` 打印 `client_dir`；
- 该目录有 `assets/`、`settings/`、`*.fairy`；
- `assets/` 下存在以 `game_key` 为前缀的包。

**失败时**：脚本会列候选并报错，不会猜。人工确认后用 `--client` 指定。

## 4. `/s1-req` 解析需求

**目的**：把 Excel 需求变成可施工的输入。**不碰 FGUI 工程**。

**输入方式 A：Excel 放 inbox**

```powershell
# 把 .xlsx 放进 .opencode/inbox/，然后
python .opencode/skills/fgui-req/scripts/excel_to_req.py
```

- 每行生成一个独立需求目录；
- 自动识别列名（资源名称/资源说明/资源类型/参考图等）；
- 提取嵌入图片到 `参考图/`；
- 生成每个需求的 `需求.md`。

**输入方式 B：手工兜底**

在 `.opencode/work/<game_key>/<需求>/` 下放：

```
需求.md        一行一需求，表头至少含「名称」「描述」
参考图/         原始截图（可选）
```

**完整链路**：

```powershell
# 1) Excel → 需求目录（或手工放好需求.md）
python .opencode/skills/fgui-req/scripts/excel_to_req.py

# 2) 机械检查（退出码 4 = 有待人工确认项）
python .opencode/skills/fgui-req/scripts/check_terms.py ".opencode/work/<game_key>/<需求>/需求.md"

# 3) 解析「一行一需求」进 清单.json 的需求[]
python .opencode/skills/fgui-req/scripts/parse_requirement.py ".opencode/work/<game_key>/<需求>/需求.md"

# 4) 参考图适配 1334×750
python .opencode/skills/fgui-req/scripts/refimage_to_canvas.py --out ".opencode/work/<game_key>/<需求>"

# 5) 生成施工单骨架
python .opencode/skills/fgui-req/scripts/build_guide.py ".opencode/work/<game_key>/<需求>/需求.md"

# 6) 生成人读清单
python .opencode/lib/workspace.py manifest-md <需求>
```

**产物**：

```
<需求>/
├─ 需求.md
├─ 参考图/
├─ 参考图_1334x750/
├─ 清单.json        需求[] 非空才算成功
├─ 清单.md
└─ 施工单.md
```

**纪律**：

- 需求写明的不再问；只有「没说且影响施工」的才进施工单决定清单，**一次问清**。
- 机械检查是确定性结果；语义判断（资源分类、冲突口径）由模型/人做。
- 美术需求截图为准，冲突逐条记录。

## 5. `/s2-fgui` FGUI 落位

**目的**：消费 s1 的 `清单.json` + `施工单.md`，把需求落到 client 工程。

**用法**：

```text
/s2-fgui <需求名>
/s2-fgui <需求名> <补充说明或截图路径>
```

**内部顺序**：

```
备事实底座 → 出方案 → 定种类 + 占位 + 清单 → 落位执行 → 🔒闸门 → 补文档 → 交程序
```

**关键动作**：

| 阶段 | 做什么 | 命令 |
|---|---|---|
| 备事实底座 | 工程改过才重扫 | `scan_fgui.py`、`lookup.py --check` |
| 出方案 | 核实到文件+节点，写 `方案.md`，备份 | `lookup.py`、`knowledge.py --topic ...` |
| 定种类/占位/清单 | 资源种类表、同规格占位、回填清单 | `placeholder_png.py`、`workspace.py manifest-*` |
| 落位执行 | 改 `assets/<包>/component/*.xml` 与 `package.xml` | 人工/模型改 XML |
| 闸门 | **停下来给人看效果** | — |
| 补文档 | 人确认后一次性补齐 | `generate_psd_spec.py` |
| 交程序 | 建快照 | `workspace.py snapshot <需求>` |

**产物**：

- client 工程的组件 XML / `package.xml`（已改）；
- `<需求>/方案.md`、`备份/`、`占位/`；
- `<需求>/清单.json` 的资源[]；
- `<需求>/FGUI/` 快照；
- 人确认后的 `校验报告.md`、`修改清单.md`、交付说明、`psd-spec.json`。

**闸门**：落位完成后必须停下。**确认效果前不写校验报告/修改清单/交付说明/psd-spec.json**；确认后一次性补齐。

**注意**：

- 只改需求涉及的包与组件；不碰 `settings/`、其它包、业务代码。
- 改前备份到 `<需求>/备份/`。
- 新图必须先过复用决策顺序；提新图必须给全规格（尺寸/透明底/九宫格/数量/命名/风格参照）。
- 占位图同名覆盖到 client 工程 `assets/<包>/atlas/`，保证工程能跑。

## 6. `/s3-to-psd` PSD 还原

**目的**：把 FGUI 某界面的布局还原成分层 PSD（给美术改图的源稿）。

**用法**：

```text
/s3-to-psd <需求>
/s3-to-psd <需求> <界面 XML 路径>
```

**优先输入**：`<需求>/psd-spec.json`（s2 产出）。没有时再手选界面 XML + 复用件清单。

**执行链路**：

```powershell
# 1) 自检 PhotoCraft
python .opencode/lib/photocraft.py --check

# 2) 解析 FGUI → 布局清单（离线）
python .opencode/skills/fgui-to-psd/scripts/_fgui_layout.py `
  --spec "<需求目录>/psd-spec.json" `
  --out "<需求目录>/_tmp/manifest.json"

# 3) 空跑看计划
python .opencode/skills/fgui-to-psd/scripts/_pc_build.py "<需求目录>/_tmp/manifest.json" --dry-run

# 4) 真搭 + 存 PSD
python .opencode/skills/fgui-to-psd/scripts/_pc_build.py "<需求目录>/_tmp/manifest.json" `
  --out "<需求目录>/psd/还原稿/<界面名>_还原稿.psd"

# 5) 结构复验
python .opencode/skills/fgui-to-psd/scripts/_psd_struct.py "<需求目录>/psd/还原稿/<界面名>_还原稿.psd"
```

**产物**：`<需求>/psd/还原稿/*.psd`；中间文件在 `_tmp/`。

**边界**：

- 只还原 FGUI 里写着的东西，不反推设计（不自己加描边/投影/渐变）。
- 不改 FGUI 工程、不导出切图。
- 复用件由用户/`psd-spec.json` 决定，图层名前缀 `复用_`。
- 遇到 `_fgui_layout.py` 告警（不支持的 gear/relation/节点类型）先停下来确认，不要硬跑。

## 7. `/s4-psd` 改样式切图

**目的**：读清单 → 查素材库 → 改 PSD 图层样式/文字/尺寸 → 导出透明 PNG → 回写 client 工程。

**用法**：

```text
/s4-psd <需求>
/s4-psd <需求> 把标签改成蓝色并导出透明图
/s4-psd <源 PSD 路径> 把按钮底图换成天蓝色，导出 out_ 图层
```

**取件顺序**：

1. 读 `<需求>/清单.json`；
2. `workspace.py find-asset <需求>` 查素材库；
3. 候选（制作单元 / 底图组 / 分类 `_预览/*.png`）由**人确认**；
4. 源 PSD 只读，复制到 `<需求>/psd/制作/<槽位名>.psd` 再改；
5. 导出前给目标单元加 `out_` 前缀；
6. 切图落 `<需求>/切图/`；
7. 定稿后 `workspace.py place <需求>` 同名回写快照 + client 工程。

**关键命令**：

```powershell
# 查素材库
python .opencode/lib/workspace.py find-asset <需求> [--id R1] [--top 3]

# 看图层/样式
python .opencode/skills/psd-style/scripts/_psd_lfx.py --layers "<psd>"
python .opencode/skills/psd-style/scripts/_psd_lfx.py --inspect "<psd>" <图层名>

# 导出透明 PNG + 回存 PSD
python .opencode/skills/psd-style/scripts/_pc_export.py "<psd>" "<需求>/切图" `
  --canvas 400x160 --texts "<需求>/_tmp/texts.json"

# 统一尺寸 + 居中
python .opencode/skills/psd-style/scripts/_fit_frames.py "<需求>/切图" --size 240x60

# 回写工程
python .opencode/lib/workspace.py place <需求>
```

**纪律**：

- 源 PSD 三来源（素材库 / 还原稿 / 用户给）**必须用户确认**；没确认前不写任何文件。
- 素材库**纯只读**；不在素材库里改原件，不重建索引。
- 组名重复时用 `lyid` 定位（`--组lyid` / `--lyid`）。
- 配色只做换算，不做设计；换算结果写进确认清单。
- 字体用 Windows 系统字体；FGUI `font=""` 推不出具体字体，字体是确认项。

## 8. 命令文件结构（维护者看）

每个命令文件是 Markdown + YAML frontmatter：

```markdown
---
description: 一句话说明
agent: fgui-flow
---

用 `skill` 工具加载 **`fgui-flow`** 技能，然后严格按它的步骤执行。

本轮的输入：

```
$ARGUMENTS
```

规则：
- ...
```

- `description`：斜杠命令列表里显示的文字。
- `agent`：由哪个 agent 执行；当前统一是 `fgui-flow`。
- `$ARGUMENTS`：用户命令后面写的内容。
- **不要把技能的详细步骤复制到命令文件**；命令只负责加载技能。

新增命令时：

1. 在 `.opencode/command/` 新建 `<命令名>.md`；
2. 写 frontmatter（`description`、`agent`）；
3. 正文只写「加载哪个技能 + 本轮输入 + 少量边界规则」；
4. 重启 opencode。

## 9. 命令之间的交接

```
/s0-env
  └─ workspace.json
/s1-req
  └─ 清单.json（需求[]）+ 施工单.md
/s2-fgui
  └─ client 工程改动 + 清单.json（资源[]）+ FGUI/ 快照 + psd-spec.json
/s3-to-psd
  └─ psd/还原稿/*.psd
/s4-psd
  └─ psd/制作/ + 切图/ + place 回写 client 工程
```

任何一步缺少上游产物时，正确做法是**回到上一步**，不要手工猜或跳过。
