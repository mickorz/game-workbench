# 01 · 总览与架构

## 1. 这套东西是什么

一套运行在 **opencode** 里的 **FairyGUI 美术流程**，由四部分组成：

```
AGENTS.md（工作区根）       每次会话自动加载的硬规矩
.opencode/agent/            主 agent（fgui-flow）：流程执行者
.opencode/command/          斜杠命令（/s0-env ~ /s4-psd）
.opencode/skills/           5 个技能：每个技能的步骤、纪律、脚本
.opencode/lib/              跨技能共享库：定位 / 快照 / 清单 / PhotoCraft 客户端
.opencode/knowledge/        动态知识库：复用、排版、资源种类、PSD 规范
.opencode/PSD素材库/        可选：可复用 PSD 源文件 + 索引
```

**它做的事**：把「策划需求 + 美术需求截图」变成 FGUI 工程里的实际改动；缺图先复用，复用不了走 AI 生图或素材库；最后把 FGUI 工程文件交给程序。

**它不做的事**：

- 不等美术出图、不找策划确认、不等程序回复（全流程一个角色干到底）。
- 不写运行时逻辑（什么时候显示、控制器页值怎么设归程序）。
- 不改 `settings/`、工程自带脚本、业务代码。
- 不替人排生图档期。

## 2. 工作区根 vs 真实工程

这是最容易搞混的一点：

| 概念 | 是什么 | 例子 |
|---|---|---|
| **工作区根** | 含 `.opencode` 的那层；**所有命令都在这里执行** | `D:\YourProject\自动化流程\` |
| **client 工程根** | 真实 FGUI 工程：`assets/` + `settings/` + `*.fairy` 所在层，由 s0 写进 `workspace.json` 的 `client_dir` | `.xflow\xc\xcodeDev\game-mahjong\client\42324\` |
| **需求目录** | 每个需求的工作目录 | `.opencode\work\<game_key>\<需求>\` |

- 脚本的相对路径一律以**工作区根**为基准。
- 要改的 FGUI 文件在 `client_dir`，不在工作区根。
- `.opencode/`、`.opencode/work/` 都是**工作层，不进交付**；交付物只有 client 工程的 FGUI 文件 + 交付说明。

## 3. 五步流程

```
s0 环境配置
   └─ 定位 client 工程 → 写 workspace.json
s1 解析需求
   └─ inbox 的 Excel / 手工需求 → 每行一个需求目录 → 清单.json + 施工单.md
s2 FGUI 落位
   └─ 备事实底座 → 出方案 → 定种类/占位/清单 → 改工程 → 🔒人看效果 → 补文档 → 快照
s3 PSD 还原
   └─ 界面 XML + psd-spec.json → 分层 PSD 还原稿（给美术改图）
s4 改样式切图
   └─ 读清单 → 查素材库 → 改 PSD → 导出透明 PNG → 回写 client 工程
```

| 步骤 | 命令 | 技能 | 主要输入 | 主要产物 |
|---|---|---|---|---|
| s0 | `/s0-env` | `fgui-env` | `xc_spce_info.json`、client 工程 | `workspace.json` 的 `client_dir` |
| s1 | `/s1-req` | `fgui-req` | `.opencode/inbox/*.xlsx` 或手工需求 | `<需求>/需求.md`、`参考图*/`、`清单.json`、`施工单.md` |
| s2 | `/s2-fgui` | `fgui-flow` | s1 的清单 + 施工单 | 改好的 client 工程、`方案.md`、`占位/`、`FGUI/` 快照、`psd-spec.json` |
| s3 | `/s3-to-psd` | `fgui-to-psd` | `psd-spec.json` 或界面 XML | `<需求>/psd/还原稿/*.psd` |
| s4 | `/s4-psd` | `psd-style` | 清单 + 源 PSD | `<需求>/psd/制作/`、`<需求>/切图/`、回写工程 |

> 命令只是「把对应技能说明书加载进来」，**不等于立刻改工程**。s2 只有一道闸门：落位完成后停下来给人看效果；确认后才补文档、生成 `psd-spec.json`、建快照。

## 4. 交接靠文件，不靠记忆

三技能之间只认一个机器真源：**`<需求>/清单.json`**。

```
s1 需求[]        → s2 决定要产出哪些资源
s2 资源[]        → s3 读界面事实（psd-spec.json）
                 → s4 逐条取件、回填 psd/切图/来源/状态
s4 place         → 切图同名回写快照 + client 工程，状态置「已替换」
```

`清单.md` 是人读版，由 `manifest-md` 从 JSON 生成，**不要手改 md**。

## 6. 六条设计原则

1. **复用优先，但判断看需求结构**：改大小 / 九宫格 / 非等比拉伸 / 旋转 / 镜像 / 改色 / 透明度 / 变灰 / 叠文字 / 用现成组件。结构对得上就复用，对不上就单独做，都不行才 AI 生图。
2. **美术需求截图为准**：与策划文字冲突时按截图做，冲突记进方案/施工单，不默默改。
3. **需求写明的不再问**：只有「没说且影响施工」的才进决定清单，一次问清。
4. **先定种类，再用同规格占位跑通**：图片 / 九宫格 / 非等比拉伸 / 位图字体 / 组件 / 复用现成。真东西到手同名同规格替换，不改节点。
5. **只用实测事实**：节点名、坐标、资源 id、图片尺寸一律来自 `lookup.py` 或 XML；`facts.json` 过期先重扫。
6. **知识库现读**：`.opencode/knowledge/*.md` 会持续更新，不凭记忆引用、不抄进技能/方案。

## 7. 角色与边界

- **agent `fgui-flow`**：主执行者。会先用一两句话确认「这次做哪一步」，再加载技能。
- **技能**：步骤和纪律的唯一出处；命令文件只负责把技能加载进来。
- **脚本**：只做确定性工作（扫描、定位、占位、清单、PSD 操作）；语义判断由模型/人做。
- **PhotoCraft**：s3/s4 的渲染后端，本机控制协议，不联网、不开浏览器。
- **程序**：运行时显示逻辑、控制器页值由程序决定；交付说明里写清即可。
